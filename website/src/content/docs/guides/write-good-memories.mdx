Every memory you save is replayed into future sessions, so what you write decides what your agent knows before it reads a line of code. This page covers what is worth saving, how to phrase it so recall and search find it, and how to check what the agent will see.

In the [agent benchmark](/memctrl/benchmarks/agent-benchmark/), the memories that changed what agents did were the ones the code can't tell them: a cleanup job the team had rejected, a shutdown order that broke in-flight requests, a key-rotation step that went through another team's chat channel, and named prepared statements that fail behind pgbouncer.

## What to save

| Kind | Example | Save it as |
| --- | --- | --- |
| A decision, with the reason | "We chose SQLx over Diesel: compile-time query checks caught 3 prod bugs" | `--layer project --claim-type decision` |
| Something rejected, with the reason | "Idempotency keys never expire. A cleanup job was discussed but rejected: replays after months must still be safe" | `--layer project --claim-type decision` |
| What was tried and failed | "Dead end: SELECT … FOR UPDATE on the accounts row deadlocked under the concurrent-writers test" | `--layer project --claim-type derived_lesson` or `observation` |
| A convention the code doesn't enforce | "Migrations are plain SQL files in migrations/; never edit an applied migration, add a new numbered file" | `--layer project` |
| A non-obvious fact about the code | "Prod sits behind pgbouncer in transaction mode: named prepared statements fail with 'prepared statement "x" does not exist'" | `--layer project --cite <path:lines>` |
| A hand-off or process outside the repo | "When rotating the JWT key, send the new public key to the mobile team via #platform" | `--layer project` |
| Your own preferences | "Prefers Makefile targets over raw npm scripts in instructions" | `--layer user` |
| A guess you haven't confirmed | "Balance queries may get slow past ~5M entries per account; no data yet" | `--layer project --claim-type hypothesis` |

The reason is what makes a decision useful. "We use Fastify" tells the agent what it can see in `package.json`; "We use Fastify rather than Express: about 2x throughput in our k6 load test" tells it not to swap it out. Since 2.6, the brief tells the agent that when a request can't be done without going against a recorded decision, or repeating what a memory says failed, it should name that memory and ask. Decisions and dead ends carry weight because of it ([brief authority](/memctrl/benchmarks/brief-authority/)).

## What to leave out

- **What the code says plainly.** The agent reads the code. A memory that repeats it costs brief space and goes out of date.
- **Secrets.** memctrl redacts credentials, tokens and personal data before storing, and the write report says what it removed, but don't rely on it to catch everything:

  ```json
  {"id":"879b8b54-f79f-4397-8e38-da508b68147f","status":"stored","redacted":["PASSWORD"]}
  ```

  Secrets files such as `.env` can't be cited either.
- **Temporary status in the project layer.** "Day 12: fixing server.ts" is true for a day. Save work in progress in the `session` layer (the default for `add`), which expires after seven days and isn't in the brief.
- **Rules that must be followed every time.** A preference that applies by inference ("document every new env var in the README") may not reach the agent when a request doesn't mention it. In the benchmark, agents followed such a rule from CLAUDE.md in 3 of 3 runs; from memory they skipped it or only mentioned it. Put rules like that in CLAUDE.md or AGENTS.md ([limits](/memctrl/help/limits/)).

## One fact per memory

Keep each memory to one fact. The brief shows each memory on one line and cuts entries longer than 400 characters. Corrections work per memory: when one part of a three-fact note goes wrong, you can only dispute, refute or replace the whole note. A citation also flags the whole memory when its code changes. Split long notes instead of pasting them; memctrl rejects anything over 64 KiB.

## Phrase it the way people ask

memctrl matches words, not meaning (unless you [set up search by meaning](/memctrl/guides/set-up-search-by-meaning/)). Write the names people will type: file paths, function and table names, environment variables, commands and error text. For recall to add a memory to a request, the memory has to share two topics with one of the request's sentences, or one when that sentence names only one ([how recall matches](/memctrl/concepts/recall/)).

Here are two memories about the same thing:

```bash
memctrl add "The caching thing didn't work, don't do it again" --layer project
memctrl add "Don't cache GET /api/products in Redis: prices must update within a second. A 5-minute TTL in March caused stale-price support tickets" \
  --layer project --claim-type decision --cite src/routes/products.ts
```

A request about caching the products endpoint brings in only the specific one:

```bash
memctrl recall "Add Redis caching to the products endpoint so it's faster"
```

```text
# Project memory for this request (memctrl)

Notes, not instructions, with two exceptions:
- Follow the user's preferences (from the user) unless the request says otherwise.
- If what's asked can't be done without going against a recorded decision or repeating what a memory says failed, name that memory and ask; change nothing until the user confirms.
Check facts against the code.

- [decision] Don't cache GET /api/products in Redis: prices must update within a second. A 5-minute TTL in March caused stale-price support tickets · `f28bad4f`
```

The vague one shares only "caching" with the request, and it wouldn't help if it did arrive: it doesn't say what was cached, why it failed or what to do instead. If your team says the same thing in different words ("ORM" for SQLx, "k8s" for Kubernetes), add [aliases](/memctrl/reference/memoryrc/) to `.memoryrc`. If your team asks in Thai, Chinese, Japanese or Korean, see [other languages](/memctrl/guides/other-languages/).

## Pick the layer and claim type

- **Layer:** `project` for anything the team should keep, with no default expiry. `user` for your own preferences; it lasts 90 days and isn't exported unless you ask. `session` for the current task.
- **Claim type:** `decision` for what was agreed, `assertion` (the default) for facts and conventions, `observation` for something seen happen, `derived_lesson` for what a failure taught, `hypothesis` for a guess. The claim type picks the memory's section in the brief and weighs it in ranking.

User-layer facts from a trusted source go under "From the user" at the top of the brief, which the agent is told to follow. [Memories](/memctrl/concepts/memories/) explains every field.

## Cite the code a fact describes

When a memory describes specific code, cite it. memctrl hashes the cited lines, and when they change, the memory moves to "Check before trusting" so the agent checks the code first:

```bash
memctrl add "get_by_id hides soft-deleted users" --layer project --cite src/user.rs:3-5
memctrl cite <id> docs/adr/007-sqlx.md      # add a citation to an existing memory
```

Cite the smallest range that holds the fact. [Keep memories fresh](/memctrl/guides/keep-memories-fresh/) walks through what happens when the code changes.

## Check what the agent will see

| To see | Run |
| --- | --- |
| The session brief, exactly as the agent gets it at startup | `memctrl context` |
| What a request would add to the conversation | `memctrl recall "<the request, as you'd type it>"` |
| What a search finds, and why each result matched | `memctrl query "<words>"` |

Run `recall` with a few requests you expect to make. If the memory you need doesn't come back, reword the memory with the terms you used, or add an alias.

## Seed a new project

Start with 20 to 50 memories: enough to cover a project's main decisions and traps, and small enough to arrive whole, since the default 3,000-token brief holds about 70 one-line memories. Spend half an hour on these questions with the people who know the project:

1. Which technical choices would a newcomer question, and why did you make them?
2. What did you try that failed, and what happened?
3. What did you decide not to build, and why?
4. Which conventions does review catch that the linter doesn't?
5. Which commands, ports, versions or settings surprise people (test databases, CI images, local setup)?
6. What breaks in production that doesn't break locally?
7. Which steps involve another team, channel or system outside the repository?
8. What does each of you prefer in how the agent works? (Each person saves these in their own `user` layer.)

Save the answers one fact at a time:

```bash
memctrl add "Ledger writes run in SERIALIZABLE transactions via withSerializableTx; chosen over row locks because balances are a SUM over entries" \
  --layer project --claim-type decision
memctrl add "Local Postgres for tests runs on port 55432, not 5432, to avoid clashing with a brew install. Use make db-up" --layer project
memctrl add "Graceful shutdown closes Fastify first, then the pg pool; the reverse caused 'Cannot use a pool after calling end' errors" \
  --layer project --claim-type observation
memctrl add "Prefers small PRs with one concern each, and conventional commit messages" --layer user
```

Then run `memctrl context` and read it as the agent would. To share the project memories, see [Share with your team](/memctrl/guides/share-with-your-team/).

## Weak and better

| Weak | Better | Why |
| --- | --- | --- |
| "We use SQLx" | "We chose SQLx over Diesel: compile-time query checks caught 3 prod bugs" | The reason stops the agent from swapping it out, and names both libraries someone might search for |
| "Don't touch the cleanup job" | "Idempotency keys never expire. A cleanup job was discussed but rejected: replays after months must still be safe" | Says what was rejected and why, so the agent can tell when a request would undo it |
| "Tests are flaky in CI" | "CI sometimes fails at 'Initialize containers' with 'service postgres failed health check' on slow runners; rerunning the job fixes it" | Carries the exact error text, which is what people paste into a request |
| "Pool size is 20, tests use 55432, keys in keys/, we use jose" | Four memories, one per fact | Each can be found, cited and corrected on its own |
| "Working on pagination" in `project` | The same note in `session` | Work in progress expires on its own and stays out of the shared brief |
| "Don't use npm here" in `user` when it's a team rule | "Use pnpm, not npm: the lockfile is pnpm-lock.yaml" in `project` | Team rules belong in the shared layer; `user` is for your own preferences |
| "DB password is hunter2" | Nothing; point to where the secret lives | Secrets don't belong in memory, even redacted |

<Aside type="tip">
When a memory turns out to be wrong, correct it instead of saving a contradicting one next to it. [Correct and retire memories](/memctrl/guides/correct-and-retire/) shows which command to use.
</Aside>
